# LFM4Ads MoE 升级：从 V1 到 V2（Shared Expert + Top-K Routing）

- **日期**: 2026-08-09
- **版本**: V2 实现完成，等待实验验证
- **状态**: 代码已就绪 / 实验待跑

---

## 1. 当前 MoE (V1) 设计评估

### 1.1 架构

```
DCNv2MoE (V1):
  Embedding (Sparse)
  ├─ CrossExpertLayer ×3   each: K=4 × Linear(360,90) + ScenarioRouter Embedding(15,4)
  │   公式: x_{l+1} = concat[g_i · W_i(x_l)] ⊙ x₀ + x_l
  │   路由: softmax(Embedding(scenario_id)) → 加权求和所有专家 (soft routing)
  ├─ DNN Linear(360,360) ×2  (+ReLU)
  └─ Head Linear(360,15)
```

### 1.2 优缺点分析

| 维度 | V1 现状 | 评价 |
|------|---------|------|
| **参数效率** | 零参数设计：4×Linear(360,90)=Linear(360,360) | ✅ 核心创新点 |
| **路由机制** | ScenarioRouter 仅 60 参数，基于场景 ID | ❌ 每个场景一个门控向量，无 token 级差异化 |
| **软路由 vs 硬路由** | Soft routing：所有专家同时激活 | ❌ 无计算节省、专家可能退化 |
| **负载均衡** | 无 | ❌ 专家可能坍塌到少数甚至一个 |
| **Shared Expert** | 无 | ❌ 缺少"共性知识捕获"机制 |
| **初始化** | Router 零初始化 → 初始化时等价 vanilla | ✅ 稳定训练 |
| **跨场景迁移** | 每个场景独立门控 → 无跨场景共享 | ❌ 小场景数据不足时门控不可靠 |
| **专家分化** | AdaTask 实验显示门控确实有分化 | ✅ 但缺乏显式促进机制 |

### 1.3 核心问题

1. **Soft routing 无稀疏性**：所有专家都计算 → 无 FLOPs 节省，专家之间靠 gate 学习分工而非强制分工
2. **无负载均衡**：训练过程中可能出现"专家坍塌"——所有 token 涌向同一个专家
3. **缺少 Shared Expert**：Qwen/DeepSeek MoE 都使用 shared + routed expert 设计，shared 捕获所有样本共性，routed 捕获专长
4. **ScenarioRouter 太弱**：每个场景只有一个固定的 4 维向量 → 同一场景内所有 sample 分到相同的 expert 权重 → 无法做 token 级路由

## 2. 前沿 MoE 设计参考

### 2.1 Qwen2 MoE

```
Qwen2MoE (per Transformer FFN block):
  Shared Expert: FFN_shared, 始终激活
  Routed Experts: K 个 FFN_routed, top-2 激活
  输出: x += shared(x) + Σ_{i∈top2} g_i · routed_i(x)
  Load balance: α · Σ f_i · P_i (Switch Transformer style)
  特点: 所有专家同维度 (hidden_dim → intermediate_dim → hidden_dim)
```

关键设计理念：
- **Shared 捕获通用知识**（语法/常识），**Routed 捕获专业知识**（数学/代码/多语言）
- Top-k 确保 sparsity → 推理时每 token 只激活 2/K 的专家 → 成本可控
- Load balance loss 防止路由坍塌

### 2.2 DeepSeek MoE

```
DeepSeekMoE:
  Fine-grained segmentation: 每个 FFN 切成 m 个更小专家（不增加总参数）
  Shared expert isolation: 共享专家单独处理，路由专家竞争
  Device-level balance + communication balance (多卡场景)
```

### 2.3 Switch Transformer

```
Switch Transformer:
  每个 token 只路由到 top-1 专家
  Capacity factor: 限制每个专家最多处理的 token 数
  Load balance loss: α · N · Σ f_i · P_i
```

## 3. V2 设计：Shared Expert + Top-K Routing

### 3.1 核心设计

```
CrossExpertLayerV2 (per Cross layer):
  ┌─────────────────────────────────────────────┐
  │  Shared Expert: Linear(360, 72) — 始终激活    │
  │  Routed Experts: K=4 × Linear(360, 72)        │
  │                  top-2 稀疏激活               │
  │  Router: Linear(360, 4) + Noise Linear(360,4) │
  │  Load Balance Loss                            │
  │                                              │
  │  零参数约束: 72 + 4×72 = 360 = dim ✓          │
  └─────────────────────────────────────────────┘

公式:
  Warmup 模式 (top_k=K=4):
    x_{l+1} = concat[shared(x_l), e₀(x_l), e₁(x_l), e₂(x_l), e₃(x_l)] ⊙ x₀ + x_l
    ≡ vanilla Cross layer (严格等价)

  Sparse 模式 (top_k=2):
    gates = softmax(top(-2) noisy_logits)  →  2 个专家激活，2 个专家=0
    x_{l+1} = concat[shared(x_l), Σ gᵢ·eᵢ(x_l)] ⊙ x₀ + x_l
    未激活专家维度: x₀ ⊙ 0 + x_l = x_l (残差直通)
```

### 3.2 对比 V1

| 特性 | V1 | V2 |
|------|----|----|
| 专家维度 | Linear(360,90) | Linear(360,72) |
| Shared Expert | ❌ | ✅ Linear(360,72) 始终激活 |
| 路由类型 | Soft (全激活) | Top-K (仅 top-k 激活) |
| 路由器 | ScenarioRouter (Embedding) | DataRouter (Linear + Noise) |
| Load Balance | ❌ | ✅ Switch Transformer loss |
| 初始化等价 | ✅ (router=0, softmax uniform) | ✅ (warmup: raw concat, no gate) |
| Warmup → Sparsify | N/A | Epoch 1: top_k=K → Epoch 2+: top_k=2 |
| Router 参数量 | 60/layer (scenario) | 2888/layer (data) |
| Router 粒度 | 场景级 (所有 token 同一 gate) | Token 级 (每个 sample 独立路由) |

### 3.3 关键设计决策

#### 3.3.1 为什么用 DataRouter 而不是 ScenarioRouter？

- **Token 级路由** > **场景级路由**：同一个场景内不同样本可能有不同偏好，ScenarioRouter 只能给场景一个固定 gate → 所有样本被同样加权 → 无法精细分工
- **代价很小**：DataRouter (Linear(360,4) ×2) = 2888 参数/层，三层合计 8664 参数 ≈ 总模型 1.3%，可接受
- **保留 ScenarioRouter 作为可选方案**：如果 data routing 过拟合 → 可切回 scenario routing

#### 3.3.2 为什么 top_k=2 而不是 top_k=1？

- top-1 (Switch Transformer) 太激进，DCNv2 Cross layer 只有 360 维，top-1 会 lose 太多信息
- top-2 是 Qwen/DeepSeek/LLaMA-MoE 的标准做法，平衡 specialization 与 coverage
- dim_routed=72 × 2 = 144 dims active out of 288 routed dims → 50% sparsity rate

#### 3.3.3 为什么用 warmup（先 top_k=K 再降为 2）？

- 初始化等价性是稳定训练的保证
- 直接从 top_k=2 初始化会导致 144 维输出为零（未激活专家），等价于随机 dropout，破坏 vanilla 等价性
- Warmup: epoch 1 全部专家 raw concat → epoch 2+ 切换 top-2 sparse routing

#### 3.3.4 未激活专家维度的处理

- 输出 = concat(shared_72d, gated_routed_k×72d, zeros_unselected)
- zeros 区域：x₀ ⊙ 0 + x_l = x_l → 残差直通
- 这些维度在下层 Cross 层中可能被不同的 top-k 选中 → 信息不丢失

#### 3.3.5 为什么不做 Feature Copy？

- Feature Copy 的设计初衷：未激活专家维度用 x₀ 对应特征填充 → 保留信息
- 当前残差直通已实现类似效果：zeros → residual x_l → 下一层可重新路由
- 如果实验显示 zeros 导致某些维度退化，后续可加入 Feature Copy

## 4. 成本分析

### 4.1 参数增量

| 模块 | V1 | V2 | 增量 |
|------|-----|-----|------|
| Sparse | ~200K | ~200K | 0 |
| Shared Expert | 0 | 3×(360×72+72) = 78,192 | +78,192 |
| Routed Expert | 3×4×(360×90+90) = 389,880 | 3×4×(360×72+72) = 311,616 | -78,264 |
| Router | 3×60 = 180 (scenario) | 3×2×(360×4+4) = 8,664 | +8,664 |
| DNN | 2×(360×360+360) = 259,920 | 同 | 0 |
| Head | 360×15+15 = 5,415 | 同 | 0 |

**总参数增量**: V2 - V1 = -72 (Shared/+Routed 抵消) + 8,664 (Router) ≈ **+8,664 (+1.3%)**

### 4.2 计算量变化

| 模式 | FLOPs/层 | vs Vanilla |
|------|----------|-----------|
| V1 (soft routing) | dim×dim × 2 ops ≈ 360×360×2 = 259K | 等价 |
| V2 warmup (raw concat) | dim×dim × 2 ≈ 259K | 等价 |
| V2 sparse (top-2) | dim×(dim_shared + 2×dim_routed)×2 = 360×(72+144)×2 = 155K | **-40%** |

V2 sparse 模式下每层少 40% FLOPs — 虽然有 360 维，FLOPs 本身很小，但这证明了 sparse MoE 的设计正确性。

### 4.3 训练成本预估

| 项目 | 估算 |
|------|------|
| Vanilla 预训练 | ~5 分钟 (2 epoch, 9.2M 行) |
| MoE V2 初始化 (load_pretrained) | ~1 秒 |
| MoE V2 微调 (2 epoch) | ~8 分钟 (与 V1 相当，Router 计算 negligible) |
| 三级下游评估 | ~2 小时 (FeatureUsage 8 场景×11 方法 + ModuleUsage 8 场景) |
| **单 seed 总时间** | **~2.5 小时** |

## 5. 代码改动清单

### 5.1 `model.py` — 新增类

- `CrossExpertLayerV2` (行 ~552-700): Shared expert + noisy top-k routing + load balance
- `DCNv2MoE_V2` (行 ~702-804): 包装 3 个 V2 Cross 层 + 2 DNN + Head
- `DCNv2MoE_V2.param_summary()`: 按模块统计参数量

### 5.2 `main_moe_v2.py` — 新增训练入口

```bash
python main_moe_v2.py [device]
```

流程：
1. 加载/预训练 vanilla DCNv2
2. 计算 vanilla per-scenario AUC baseline
3. 初始化 DCNv2MoE_V2 (from vanilla weights)
4. Epoch 1: top_k=4 warmup → 等价 vanilla
5. Epoch 2+: top_k=2 sparse routing + load balance loss
6. Per-scenario AUC 对比 (Vanilla vs MoE V2 vs MoE V1)
7. 下游评估 (FeatureUsage/ModuleUsage)
8. 专家分化分析 (gate statistics per scenario)

输出：
- `result_moe_v2.csv`: per-scenario AUC 对比
- `result_moe_v2_downstream.csv`: 下游评估对比
- `cache/gate_stats_v2.json`: 专家门控统计

## 7. 预期结果与猜想

### 7.1 V2 > V1 的理由

1. **Token 级路由**：DataRouter 比 ScenarioRouter 更精细 → 尾部场景（#3, #5）受益
2. **Shared expert**：捕获跨场景共性 → 大流量场景（#0, #1, #4）有稳定基准
3. **Load balance**：防止专家坍塌 → 每个专家都被用到 → 更多样化的特征表示
4. **Top-k sparsity**：硬分配促进专家专长分化

### 7.2 V2 可能不如 V1 的场景

1. **极稀疏模式 (top_k=2)**：144 维残差直通 → 如果这些维度承载重要特征 → 掉点
2. **Router 过拟合**：DataRouter 2888 参数/层 vs 60 参数 ScenarioRouter → 小场景可能过拟合
3. **Warmup 后突变**：epoch 2 突然从 top_k=4 变为 top_k=2 → 门控可能不稳定

### 7.3 最可能提点的场景

- **场景 #3**：小场景 (0.32%)，当前 ScenarioRouter 固定 gate 无法适配 → DataRouter token 路由可能改善
- **大流量场景**：Shared expert 提供稳定基础 → 加上 routed expert 的增量可能优于纯 soft routing

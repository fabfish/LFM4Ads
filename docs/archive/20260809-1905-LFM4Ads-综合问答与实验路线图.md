### 1.3 梯度统计脚本设计（2026-08-09 修订：改用 RMS-per-param 口径）

> **修订说明（D9 审核）**：本节初版把「参数数量占比」直接当作「梯度范数占比」的预期基线，
> 该推断**不成立**，已整体重写。原表格与「Cross Expert 应占 non-Sparse 梯度约 60%」的判据作废。

#### 1.3.0 先厘清 `Sparse` 是什么（常见误解）

`Sparse` **不是** MoE 的任何部分，它是**类别特征 embedding 表**：

```python
class Sparse(nn.Module):           # model.py:8-17
    for field, size in (fields.user | fields.video).items():
        self.tables[field] = nn.Embedding(size, 10)   # 36 个 field 各一张表
```

MoE 专家（`CrossExpertLayer` / `CrossExpertLayerV2`）只是把 `Linear(360,360)`
切成 `K × Linear(360, 360/K)`（V2 为 shared + K routed），**与 embedding 表无关**。

因此「MoE 占大头吗」取决于口径：

| 口径 | Cross Expert 占比 | 结论 |
|------|:----------------:|------|
| **占总参数** | 0.46% | ❌ 不占大头——99.2% 是 Sparse embedding |
| **占 non-Sparse 可训练参数** | 59.5%（389,880 / 655,395） | ✅ 在「排除 embedding 之后」是训练更新的大头 |

本节关心的是后者：MoE 在**可训练非-Sparse 容量**里的主导度。

#### 1.3.1 为什么「参数比 = 梯度比」是错的

初版的错误有三层：

1. **量纲混淆**：脚本返回的是 `sqrt(v_g)/sqrt(total)`，即**梯度范数**之比；而参数占比
   59.5% 对应的是**平方范数**占比。即便在「每元素梯度方差相同」的理想假设下，
   范数比也应是 √0.595 ≈ **77%**，而不是 60%——原文的 60% 与代码口径自相矛盾。
2. **假设不成立**：DNN(`Linear 360×360`)、Cross Expert(`360×90`)、Head(`360×15`)、
   Router(`Linear 360×K` / `Embedding`) 处于网络不同深度、有不同的激活与缩放，
   per-element 梯度量级根本不统一，用参数数量预测不了梯度范数。
3. **判据无依据**：因而「低于 60% ⇒ Expert 更新不足」没有任何理论支撑，
   不能作为调 LR / β₂ 的依据。

同理，原「预期 grad L2 占比」表（Sparse ~99.2% / Cross Expert ~0.28% / …）
只是参数比的复述，**不是梯度预测**，一并作废。

#### 1.3.2 正确度量：每参数 RMS 梯度

要回答「某组参数是否更新不足」，必须做**参数量归一化**，比较每组的**每参数 RMS 梯度**：

$$\mathrm{RMS}_g \;=\; \frac{\lVert \nabla_\theta L \rVert_2^{(g)}}{\sqrt{N_g}} \;=\; \sqrt{\frac{v_g}{N_g}}, \qquad v_g=\textstyle\sum_{\theta\in g}\lVert\nabla_\theta L\rVert_2^2$$

判据（横向比较，无绝对阈值）：

| 观察 | 判读 |
|------|------|
| `RMS(Cross Expert) ≈ RMS(DNN)` | 专家与 DNN 更新强度相当，健康 |
| `RMS(Cross Expert) ≪ RMS(DNN)`（如 <1/3） | 专家更新不足 ⇒ 提高 expert LR 或降低 β₂ |
| `RMS(Router) ≪ RMS(Expert)`（如 <1/10） | 路由几乎不学 ⇒ 路由退化为均匀，MoE 名存实亡 |
| `RMS(Shared) ≫ RMS(Routed)`（V2） | 共性知识由 shared 承担，routed 未分化 |
| 同一 expert 在各 scenario 的 RMS 方差大 | **特殊化**证据（该专家被特定场景主导） |
| 各 expert 的 scenario-RMS 分布近似一致 | **均衡化**证据（无分工） |

组范数占比（`sqrt(v_g/Σv)`）仍会一并输出，但只作**辅助**参考，不作判据。

#### 1.3.3 脚本接口

`scripts/diagnose/measure_gradient_dominance.py`：

```python
GROUPS = {                                        # 组判定（V1/V2 通用）
    'Sparse':       lambda n: n.startswith('sparse'),
    'CrossExpert':  lambda n: 'cross_layers' in n and '.experts.' in n,
    'CrossShared':  lambda n: 'cross_layers' in n and '.shared.' in n,
    'Router':       lambda n: 'w_gate' in n or 'w_noise' in n or '.router.' in n,
    'DNN':          lambda n: n.startswith('dnn') or n.startswith('layers.3') or n.startswith('layers.4'),
    'Head':         lambda n: n.startswith('head') or n.startswith('layers.5'),
}

def measure_rms_dominance(model, dataset, n_batches=20) -> dict:
    """返回:
      groups: {group: {n_params, grad_sq, rms, norm_share}}   # rms = sqrt(grad_sq/N)
      per_expert_scenario: {(layer, expert, scenario): rms}   # 特殊化分解
      verdict: {'expert_vs_dnn': ratio, 'router_vs_expert': ratio, 'specialization': cv}
    """
```

- 按 scenario 切 sub-batch 分别 backward（复用 `train_moe` 的范式），
  从而同时得到 per-(layer, expert, scenario) 的 RMS 分解。
- 只做前向+反向、不 `optimizer.step()`，不改变 checkpoint。
- 输出 `cache/grad_dominance_<exp>.json`。

## Q3：场景 #3 深度分析

### 3.1 数据描述

| 指标 | 数值 |
|------|------|
| 场景编号 | 3 |
| 训练集样本数 | 31,476 行 |
| 验证集样本数 | 5,751 行 |
| 测试集样本数 | 3,404 行 |
| 测试集占比（全部数据） | 0.32%（最小场景之一） |
| 场景相对权重 | 低流量 / 长尾场景 |

### 3.2 核心现象

#### 现象 1：AdaTask 中 none 唯胜于场景 #3

| 模式 | S3 AUC | 8 场景均值 |
|------|:------:|:---------:|
| none | **0.7415** | 0.7087 |
| encourage | 0.7281 | 0.7210 |
| suppress | 0.7192 | 0.7200 |

**none > encourage > suppress**，且 S3 是唯一一个 none 获胜的场景。其他 7 个场景中 encourage 赢 6 个、suppress 赢 S8。

#### 现象 2：持续学习中场景 #3 遗忘最严重

| 模型 | 预训练→最终 | 遗忘量 Δ |
|------|:-----------:|:-------:|
| Vanilla S3 | 0.7251 → 0.6231 | **−0.1020** |
| MoE S3 | 0.7449 → 0.6937 | −0.0512 |

Vanilla 在 S3 的绝对 AUC 降幅是所有场景中最大的（−0.1020），MoE 缓解了一半（−0.0512），但仍显著下降。

### 3.3 假说分析

#### 假说 1：梯度尺度假说（AdaTask AU 被 S3 小样本噪声扭曲）

**机制**：S3 仅 31,476 条训练样本（占总量 ~3%），sub-batch 内 S3 样本极少。AdaTask 中每个 sub-batch 独立计算 AU，而 AU 对稀疏 sub-batch 的梯度估计不稳定——高方差导致 LR 调制（encourage/suppress）的"信号"被噪声淹没。

**证据**：
- encourage/suppress 依赖 AU 计算 per-expert 的 LR 缩放因子，AU 的方差直接影响调制质量
- S3 的 sub-batch 最小（~3% × 16,384 ≈ 492 样本），AU 估计的方差 ∝ 1/√n，小 n 导致高方差
- none 模式不对 LR 做调制，不受 AU 噪声影响 → 在 S3 上表现最好 → 支持假说

**验证方案**：
1. 统计 S3 sub-batch 的 AU 分布（均值、标准差），对比大场景
2. 测量 S3 sub-batch 的梯度范数，对比均值
3. 消融：用 S3 全量 AU（非 sub-batch AU）做调制

#### 假说 2：持续学习竞争（场景冲突→遗忘）

**机制**：S3 训练时"学进去"了（MoE S3 LA = 0.7655），但后续场景（尤其 S8，最大场景）的训练参数更新方向与 S3 冲突，导致覆盖性遗忘。

**证据**：
- 持续学习按场景顺序训练（S0→S1→...），每个场景单步更新，无 replay
- S8 是最大场景（训练集 ~2.4M），其梯度量级远超 S3
- Vanilla S3 掉 −0.1020 而 MoE S3 掉 −0.0512 → MoE 的专家分工部分隔离了冲突，但仍有遗忘
- S8 MoE LA 从 0.7618 → 0.6944（−0.0674），说明 S8 作为最终训练场景，也会被 S0–S6 训练后遗忘

**验证方案**：
1. 改变训练顺序（把 S3 放最后），观测遗忘剖面
2. 多 order 实验（D5 中已提到但未完成）
3. 梯度 cosine similarity：测量连续场景间的参数梯度方向冲突度

#### 假说 3（复合）：encourage+suppress 混合猜想

**设想**：对 S3 sub-batch 内各专家分别处理——强 AU 专家 apply encourage（保持已有知识）、弱 AU 专家 apply suppress（让出容量给共性知识）。

**可行性分析**：

| 维度 | 评估 |
|------|------|
| 机制合理性 | ⚠️ encourage 和 suppress 对 LR 的方向相反，per-expert 混合在数学上等价于重新设计调制函数 |
| 实现复杂度 | 低（修改 AdaTaskOptimizer 的 AU→LR 映射即可） |
| AdamW 二阶矩抵消 | ⚠️ 风险：AdamW 的 v_t 累积历史梯度二阶矩，瞬间的 LR 调制会被 v_t "平滑"掉，实际效果可能被稀释 |
| 理论等价性 | encourage+suppress 混合 = 统一调制函数 g(AU_i) = AU_i^α / min(AU_i^α) · (1 if i in strong else -1) + constant，简化后只是不同门限的变种 |

**建议**：在 E5（suppress）已有结果后，先跑 α sweep（0.5/0.75/1.0/1.5/2.0）而非混合，因为 α 控制调制强度，可能比模式切换更有效。

## Q4：MoE 设计调整方向

### 4.1 top-k vs soft routing（已实现）

**当前状态**：MoE V2（`CrossExpertLayerV2` + `DCNv2MoE_V2`）已实现 top-2 sparse routing + warmup 机制，代码在 `model.py`，入口在 `main_moe_v2.py`。

| 维度 | Soft Routing (V1) | Top-K Sparse (V2) |
|------|:-----------------:|:-----------------:|
| 激活专家数 | K=4 (全激活) | top_k=2 → 50% 稀疏 |
| 零参数约束 | ✅ | ✅（dim_shared + K×dim_routed = dim） |
| Warmup 等价 vanilla | ✅（全激活 = concat） | ✅（warmup 阶段 top_k=K） |
| Load Balance | ❌ | ✅ Switch-style auxiliary loss |
| Router 噪声 | ❌ | ✅ 训练时 noisy gating 增加探索 |
| 计算量 | 4×Linear(360,90) = 129,600 FLOPs | 2×(72+72) = 51,840 FLOPs (inference) |
| 尾部场景风险 | 低（全激活） | ⚠️ 稀疏路由可能"忽视"小场景 token → 需 load balance 兜底 |

**建议优先级**：P2 — 代码已就绪，需实验验证 sparse 不伤害尾部场景。

### 4.2 Feature Copy 可行性分析

**定义**：MoE Cross 层的输出是否需要对 x₀（原始 embedding）做 feature copy（类似 resnet 的 shortcut + 门控选择）。

**当前代码**：MoE forward = `(shared(x) + Σ gate_i × expert_i(x)) * x₀ + x`。其中 `* x₀` 是 DCNv2 自带的 cross 操作，已经做了 feature-level interaction。

**是否需要额外 feature copy**：
- 不需要：DCNv2 的 `x_{l+1} = x₀ ⊙ f(x_l) + x_l` 已经保证了 x₀ 信息在各 Cross 层中流通，无需另加 gate
- 可能有益：在 Downstream FeatureUsage gate 模式下，对 MoE 输出做**选择性 copy**——gate 值高时保留更多 x₀ 特征，gate 值低时让专家输出主导。但这等价于给 shared expert 加一个 gated copy 分支。

**建议**：P4（低优先级），在 top-k + load balance 都验证后，如果专家分化不足，再考虑 feature-gated copy 作为增强手段。

### 4.3 从零预训练的代价预算

**当前 MoE 训练流**：从 `dcnv2_vanilla.pt` 加载 → 微调 2 epoch（~1–2h/seed）。

**从零预训练的额外代价**：

| 指标 | 微调（当前） | 从零预训练 |
|------|:----------:|:---------:|
| 初始状态 | vanilla Cross → MoE split | 随机初始化 |
| 收敛 epoch 估算 | 2 epoch | 4–8 epoch |
| 训练集大小 | ~9.2M (train only) | ~9.2M |
| batch_size | 16384 → ~560 steps/epoch | 563 step/epoch |
| 时间/seed | ~1.5 h | ~6 h（4 epoch） |
| 风险 | 预训练等价性保证 | 专家从零学可能坍塌 |

**从零预训练额外复杂度**：
- 必须自带 load balance + warmup（否则专家可能在早期坍塌到一个专家）
- warmup 阶段：top_k=K（soft routing，等价 vanilla），之后 gradually sparsify
- 需要的 warmup 策略在 `main_moe_v2.py` 中已有实现

**建议**：P3 — 当前微调 pipeline 已足够，从零预训练作为"完整训练范式"验证，放在 P1+P2 完成后。

### 4.4 设计调整汇总

| 调整方向 | 优先级 | 状态 | 预期收益 | 风险 |
|----------|:------:|:----:|----------|------|
| top-k sparse routing + load balance | P2 | ✅ 代码就绪 | 专家硬分工 + 省算力 | 尾部场景可能退化 |
| K 消融 (K=2/4/6/8) | P3 | ⏳ 未做 | 找最优专家数 | 更多专家 = 更碎 |
| 从零预训练 MoE | P3 | ⏳ 未做 | 完整训练范式 | 坍塌风险 |

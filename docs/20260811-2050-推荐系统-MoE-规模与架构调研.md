# 推荐系统 MoE 工作调研：模型规模与架构细节统计

> 调研时间：2026-08-10 ｜ 范围：2023–2026，头部互联网大厂优先
> 口径说明：除特别标注外，参数量均指 **dense 网络参数（不含 embedding table）**。这是本领域最大的数字陷阱，见 §6.1。

---

## 0. 一句话结论

**在线部署的稀疏 MoE 排序模型，当前最优配置收敛在：总参 4–7B / 激活 0.5–2.3B（稀疏比 1/2 ~ 1/8），专家数判别式 4–16、生成式 24–54（含 1 个共享专家），token 级 top-k 路由 + loss-free 负载均衡，MoE 只放在深层 FFN。**
规模天花板不由算法决定，而由**训练数据天数**和**延迟预算**决定——这是本次调研最硬的一个发现（§5）。

---

## 1. 三条互不相同的技术路线（先分清，否则数字没法比）

推荐领域的"MoE"是一个被严重超载的词，指三种完全不同的东西：

| 路线 | 代表 | 专家是否稀疏激活 | 路由粒度 | 目的 |
|---|---|---|---|---|
| **A. 多任务软 MoE** | MMoE、PLE/CGC、STEM、AdaTT、LiRank | ❌ 全部专家都算（dense） | task-level（每任务一个 gate） | 解决多目标跷跷板 |
| **B. 判别式排序塔稀疏 MoE** | RankMixer、TokenMixer-Large、MTGR | ✅ top-k 稀疏 | feature-token-level | 参数扩容但不涨推理成本 |
| **C. 生成式推荐稀疏 MoE** | OneRec-V1/V2、PLUM、HD-Rec | ✅ top-k 稀疏 | token-level（LLM 式） | 走 LLM scaling law |

路线 A 已经是十年前的存量技术，**它的"专家"和 Switch/DeepSeek 意义上的专家完全不是一回事**——A 里的专家全部参与前向，参数量和 FLOPs 同步增长，根本没有"稀疏"。真正的增量在 B 和 C。本报告重心在 B、C。

## 3. MoE 架构细节的横向统计

### 3.1 专家数与 top-k

| 场景 | 专家总数 | top-k | 共享专家 | 说明 |
|---|---|---|---|---|
| 判别式排序塔 | **4 – 16** | 2 左右 | 1（TokenMixer-Large） | 专家粒度**粗**，因为 token 数本身就少（几十个特征 token） |
| 生成式推荐 | **24 – 54** | 2 – 3 | 1（V2 起） | 向 LLM 靠拢，细粒度专家 |
| LLM 骨干复用 | 8 – 256 | 2 – 8 | 1 | PLUM / 360Brew 直接继承 Gemini、Mixtral 的配置 |

### 3.2 已形成共识的四件事

1. **共享专家（shared expert）是标配**。TokenMixer-Large、OneRec-V2、HD-Rec 全部采用 "1 shared + k−1 routed"。作用是在路由失误时兜底，等价于给 MoE 加了一条 dense 残差。
2. **负载均衡从 aux loss 迁移到 loss-free**。2025 下半年之后的工作（OneRec-V1/V2）普遍沿用 DeepSeek-V3 的无辅助损失偏置调整；只有较早或较学术的工作还在用 aux loss + 权重调参。
3. **MoE 只放深层，浅层保持 dense**。OneRec-V2 明确"前几层 Dense FFN，深层替换为 MoE"；这与 Llama 4 的交替层设计同源——浅层做通用表征需要全员参与，深层才适合分工。
4. **MoE 位置一律在 FFN，不在注意力**。唯一例外是阿里 LoopCTR（arXiv 2604.19550）把 MoE 同时放进注意力的 V/O 投影层和 FFN，两套 MoE 共享同一个路由器。

### 3.3 一个已被推翻的做法：DTSI

这是本次调研中**最值得注意的技术路线修正**：

- **2025 年 RankMixer** 提出 **DTSI（Dense Training, Sparse Inference）**——训练时所有专家都算保证充分训练，推理时才稀疏。配合 ReLU 路由解决了推荐场景的"专家饿死"问题，当时是亮点。
- **2026 年 TokenMixer-Large**（同一个字节团队）在摘要里直接把 DTSI 定性为 **"incomplete MoE sparsification"（不完整的稀疏化）**，改为 **sparse training + sparse serving**，靠三个技巧稳住训练：
  - **First Enlarge, Then Sparse**：先把 dense 模型训到最优，再把 per-token SwiGLU 拆成细粒度子专家（而不是一上来就堆专家数）
  - **Gate value scaling α**：路由输出前乘 α 放大梯度，α 与稀疏率成反比（1:2→α=2，1:4→α=4）
  - **Down-matrix small init**：SwiGLU 末层投影矩阵初始化标准差从 1.0 降到 **0.01**（ReZero 思路），让模块早期近似恒等映射

> **我的判断**：如果你在做推荐 MoE 的训练稳定性研究，DTSI 已经不是终点了，`enlarge-then-sparse + gate scaling + small init` 这套组合是目前工业界最新的答案。DTSI 的代价是训练成本仍按 dense 算，在 7B 以上根本训不动，这才是它被放弃的真实原因。

### 3.4 路由粒度的演进

```
task-level (MMoE 2018 / PLE 2020 / STEM 2024)
   ↓  每个任务一个 gate，专家全算
feature-token-level (RankMixer 2025 / TokenMixer-Large 2026)
   ↓  把异构特征切成 token，每个 token 独立路由
token-level (OneRec 2025 / PLUM 2025)
   ↓  完全 LLM 化的 per-token top-k
sequence/theme-level (Meta MoS, WWW'26)
      按用户兴趣主题拆子序列再路由 —— 新方向
```

Meta 的 MoS 是唯一跳出"逐 token 路由"框架的：它路由的不是 token，而是**整段主题一致的子序列**。这条路线目前只有 100M 量级的验证，但概念上正交于前三种，可以叠加。

## 4. 稀疏比：一个有争议的参数

| 工作 | 稀疏比 | 结论 |
|---|---|---|
| RankMixer | 1/8 | 激活 1/8 专家仍保留 dense 1B 几乎全部精度 |
| TokenMixer-Large | **1:2 上线** | 1:2 ROI 最高、近乎零掉点；**1:4 轻微下降；1:8 负载均衡恶化，仍在探索** |
| OneRec-V1 | ~13% (≈1:8) | 正常工作 |
| OneRec-V2 | 0.5B/4B = 12.5% (≈1:8) | 正常工作 |

**同样是 1:8，字节说崩、快手说没事——这个矛盾值得解释**：字节是在**特征 token**（几十个，语义高度异构，且长尾特征天然低频）上做路由，token 数少 + 分布极不均衡，稀疏到 1/8 时路由器根本收不住；快手是在**语义 ID token**（同质、分布相对均匀）上做标准 LLM 式路由，53 个细粒度专家提供了足够的路由自由度。

> **推论**：稀疏比的可行下界由 **token 数量 × token 分布均匀性 × 专家粒度** 共同决定，不能跨场景照搬。判别式排序塔想压到 1/8，得先把专家切细、并解决特征长尾导致的路由塌缩。**这是一个明确的开放问题，也是当前最值得做的方向之一。**

## 5. "最优规模"到底由什么决定

结论：**不是算法，是数据天数和延迟预算。**

**证据一 · TokenMixer-Large 直播场景的收敛天数表（Table 4）**

| 参数量 | 收敛所需数据 | ΔUAUC（对上一档） |
|---|---|---|
| 30M → 90M | 14 天 | +0.94% |
| 90M → 500M | 30 天 | +0.62% |
| 500M → 2.3B | 30 天 | +0.41% |
| 500M → 2.3B | **60 天** | **+0.70%** |

同一个 2.3B 模型，数据从 30 天加到 60 天，增益从 +0.41% 回到 +0.70%。**参数不是不管用，是喂不饱。**

**证据二 · 字节按场景给出的规模天花板**

| 场景 | 离线规模 | 在线规模 |
|---|---|---|
| Feed 广告 | 15B | **7B** |
| 电商 | 7B | **4B** |
| 直播 | 4B | **2B** |

同一套架构，三个场景差 3.5 倍——差别来自各场景的样本量和 QPS/延迟预算，不是模型能力。

**证据三 · 收益拐点**
- OneRec-V2：4B dense loss 3.20 → 8B dense 3.19，**参数翻倍只降 0.01**
- TokenMixer-Large：4B +1.14% → 7B +1.20%，**参数近乎翻倍只涨 0.06pp**

**综合判断（建议直接引用）**

| 指标 | 当前最优区间 |
|---|---|
| 在线部署总参数 | **1B – 7B**（多数场景 2–4B） |
| 在线激活参数 | **0.5B – 2.3B** |
| 离线探索上限 | **8B – 15B**（超过即饱和） |
| 稀疏比 | **1/2（判别式稳妥）～ 1/8（生成式可行）** |
| MFU 目标 | **45% – 60%**（低于 20% 说明架构有问题，不是规模问题） |
| 延迟约束 | 排序塔 ~15ms 不可破 |

## 6. 三个容易踩的坑

### 6.1 参数量口径混乱（最大的坑）

- Meta HSTU 论文里的 **"1.5 万亿参数"包含 embedding table**。推荐系统的 embedding 动辄占 99% 参数量却几乎不产生 FLOPs，把它算进"模型规模"再去和 LLM 比 scaling law，是错误对标。
- 字节 RankMixer / TokenMixer-Large 报的是 **dense 网络参数**（16M → 1.1B → 7B），这才是可比口径。
- 快手 OneRec 报的是 **模型参数（不含 embedding/codebook）**。

**做对比研究时，务必先确认口径，否则会得到"推荐模型比 GPT-4 还大"这种荒谬结论。**

### 6.2 MMoE/PLE 类工作不该和稀疏 MoE 混在一张表里

它们的"专家数"是 dense 全算的，参数量和 FLOPs 线性同增，讨论"激活参数"没有意义。见 §1。

### 6.3 二手解读的数字不可信

调研中遇到大量中文技术博客写 "OneRec 每层 128 个专家""1B 模型激活 230M"——**这些数字在论文原文中都不存在**。OneRec-V1 是 24 专家，V2 是 53+1。凡引用请回原文（本报告表中数字均已回原文或官方技术报告核对）。

## 7. 国内 vs 海外的路线差异

| | 国内（字节 / 快手 / 美团 / 腾讯） | 海外（Meta / Google / Netflix / Pinterest / LinkedIn） |
|---|---|---|
| 排序塔是否自建稀疏 MoE | **是**，且已全量上线（RankMixer、TokenMixer-Large、MTGR） | **基本没有**。排序侧仍是 dense scaling 或 task-level 软 MoE |
| 稀疏 MoE 出现在哪 | 排序塔 + 生成式 decoder，都是自研路由 | 只在**复用的 LLM 骨干里自带**（PLUM 用 Gemini-1.5 MoE、360Brew 用 Mixtral 系） |
| 主流扩容手段 | 稀疏 MoE（参数涨、算力不涨） | dense transformer 扩容（HSTU、Netflix 1B、PinFM 20B、Yandex 1B）或外部蒸馏（Meta ExFM，教师 0.8–3.2T） |
| 数字披露程度 | 高，给 scaling 曲线、MFU、延迟、GMV | 中低，Netflix/Meta 官方博客多为定性 |

**成因判断**：国内大厂排序塔的算力预算和迭代节奏更激进，且延迟预算被压得极死（15ms），"参数扩容但 FLOPs 不涨"的稀疏 MoE 正好卡在这个约束上；海外更倾向用统一基础模型 + 蒸馏的方式绕开在线延迟问题，稀疏性交给上游 LLM 去解决。

## 8. 给研究者的选型建议与开放问题

**如果要复现 / 做基线：**
- 判别式排序：从 **TokenMixer-Large 的 1:2 SP-MoE** 起步（4.6B 总 / 2.3B 激活），配 gate scaling α=2 + down-matrix init 0.01
- 生成式推荐：从 **OneRec-V2 的 53+1 top-3 / 4B 总 0.5B 激活** 起步，浅层 dense、深层 MoE，loss-free 均衡

**四个我认为值得做的开放问题：**
1. **判别式排序塔的极限稀疏比**。字节在 1:8 上明确失败（负载均衡恶化）。特征 token 的长尾分布导致路由塌缩，这个问题没人解决，做出来就是一篇好文章。
2. **专家粒度 vs token 数量的定量关系**。为什么 53 个细粒度专家能撑住 1/8，16 个粗粒度专家撑不住？目前只有经验，没有理论。
3. **MoS 的主题级路由能否与 token 级路由叠加**。目前只在 ≤100M 上验证过，工业规模未知。
4. **数据受限下的最优规模**。§5 显示规模瓶颈是数据天数，但没有任何工作给出 "N 参数需要 D 天数据" 的定量关系——推荐版的 Chinchilla law 还是空白。

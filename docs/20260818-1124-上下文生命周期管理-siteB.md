# 第二台机器：上下文生命周期管理探索文档

> 记录时间：2026-08-18 11:24（本地时间）
> 性质：工作方式约定（非实验结论），供 site B 的每个新对话遵循。
> 一句话规则：**一次对话只选一个模型、只 plan 并解决一轮问题；解决后立即落盘更新文档，然后结束本对话，换一个新对话。**

## 0. 为什么需要这条约定

1. **上下文随对话增长而失真**。一个对话做得越久，早期事实、冻结口径、中间决策越容易在记忆里漂移，最后与落盘文档不一致。
2. **证据链靠文档而非记忆**。仓库已经要求结论必须可溯源（术语、四元组、端点、证据路径）。只有"解决一轮 → 落盘 → 结束"，下一轮才能从文档而非模型记忆恢复。
3. **节约 token**。长对话反复携带同一段历史，成本高且没有新增信息；短对话让每次输入只含当下问题 + 一份权威文档。
4. **失败可定位**。一轮问题一个文档增量，出错时 diff 一目了然，不会把多个决策的后果混在一个无法拆分的会话里。

## 1. 生命周期模型

一次对话的完整生命周期是五步：

```text
选定一个模型 + 一个明确问题
        │
        ▼
   plan（计划与冻结口径）
        │
        ▼
   解决这一轮问题（改代码 / 跑实验 / 做诊断）
        │
        ▼
   落盘：更新文档 + git add + commit + push
        │
        ▼
   结束本对话（显式声明"上下文生命周期中止"）
        │
        ▼
   换新对话，从文档恢复，处理下一轮
```

## 2. 硬约束

1. **一轮一个问题**：一个对话只处理一个可闭环的目标（一次诊断、一个实验阶段、一份文档、一次 bug 修复）。发现新问题记入文档的 backlog，不在同一对话里顺手展开。
2. **plan 必须冻结口径**：开始动手前，把要改什么、证据边界、判定规则、端点、随机种子写进预注册或计划，不在执行中途改口径。
3. **落盘是"完成"的定义**：没有写入文档 + 提交推送，这一轮不算完成；未落盘的代码和结论视为不存在。
4. **代码完成即提交**：任何代码或配置修改通过针对性检查后，立即单独 `git commit`，不攒到对话末尾。
5. **显式结束**：落盘并推送后，回复中必须明确写出"本次上下文生命周期中止"，并列出交给下一轮的入口文档与 backlog。

## 3. 每次落盘必须更新什么

| 对象 | 内容 | 去向 |
|---|---|---|
| 实验文档 | 目标、口径、结果表格、结论、证据路径、backlog | `docs/YYYYMMDD-HHMM-主题-siteB.md` |
| 结论/预注册 | 冻结的端点、判定、四元组 | 同上，或独立预注册文档 |
| 机器状态 | 阶段门禁、审计 JSON、汇总 JSON | `cache/task_role_optimizer_27k_siteB/` |
| 代码与配置 | 实现、协议、脚本 | 仓库文件，独立 commit |
| backlog / 下一步 | 未解决问题、下一轮入口 | 文档末尾「后续」章节 |

## 4. 新对话如何恢复

新对话开始时，不依赖模型记忆，而是按顺序读：

1. 本仓库 `AGENTS.md`（总规则）；
2. `docs/NEXT.md` 或最近一次结论文档的「后续」章节（下一步）；
3. 本轮相关的预注册文档 + 结构化证据 JSON。

恢复完成后，先复述"我现在要解决哪一轮、依据哪份文档"，再开始 plan。

## 5. 边界与例外

- 一个实验阶段若天然需要"启动 + 监控到完成"，仍属一轮问题，可以在同一对话内完成，但每产生一次代码改动都必须即时 commit，最终结论一次性落盘。
- 只有当一轮问题在 plan 阶段就发现必须拆成多轮时，才在本对话结束前把拆分结果写进文档 backlog，并立即结束；不在同一对话里顺延处理下一轮。

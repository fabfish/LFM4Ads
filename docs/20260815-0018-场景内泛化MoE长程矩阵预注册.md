## 一、为什么此前所有 MoE 实验必然测不出收益（根因）

零成本分解冻结 dense 基线（`dcnv2_vanilla.pt`）：

| 指标 | 值 |
|---|---|
| **pooled AUC**（此前所有实验的主终点） | **0.7775** |
| 只用「场景先验 CTR」预测（完全不看 user/video 特征） | **0.6363** |
| **场景内 macro AUC**（8 场景等权） | **0.6736** |
| 场景内样本加权 AUC | 0.7265 |

训练样本分布与 CTR：

| scenario | train 占比 | test CTR | 场景内 AUC |
|---|---|---|---|
| 1 | **65.63%** | 0.4366 | 0.7315 |
| 0 | 20.79% | 0.1167 | 0.7077 |
| 4 | 7.60% | 0.5436 | 0.7133 |
| 2 | 3.50% | 0.3690 | 0.7786 |
| 6 | 1.53% | 0.1468 | 0.7261 |
| 3 | 0.34% | 0.0206 | 0.7251 |
| 8 | 0.15% | 0.0344 | **0.6799** |
| 5 | 0.14% | 0.2008 | **0.6764** |
| *12（辅助）* | 0.09% | 0.0994 | **0.5704** |
| *7（辅助）* | 0.03% | 0.5839 | **0.4268 ← 低于随机，预测方向是反的** |

**两个事实合起来解释了"两千块钱跑不出一个 work case"**：

1. **pooled AUC 的一大半是「认出这是哪个场景」白拿的**（CTR 跨场景差 26 倍，仅用场景先验就有 0.6363）。
   真实的场景内排序只有 0.6736。
2. **MoE 的收益机制（参数隔离 → 减少跨场景干扰）100% 作用在场景内排序上**，而小场景
   （s5+s7+s8+s12）合计只占 test 的 **0.5%**。即使把 s7 从 0.43 救到 0.73（+0.30 的巨大改善），
   pooled AUC 也只动 **~0.0001** —— **永远埋在自定的 0.001 噪声地板之下**。

**结论：这不是调参失败，是主终点的分辨率与收益的作用位置错配。** s7 的 AUC < 0.5 意味着模型在该
场景上预测是反的，这是**负迁移的直接证据**——一套共享参数被占 65.6% 的 s1 梯度拽着走。

> 与文献一致：MMoE / PLE / STAR 报告的都是 per-scenario / per-task 指标，没有报 pooled AUC 的。

### 1.1 与既有结论的关系（不冲突）

| 既有结论 | 是否受影响 |
|---|---|
| cross 层容量非瓶颈（dense-widened 4×） | **不受影响**。本实验**不加任何容量**（见 §2） |
| capacity-MoE 关闭（容量 0 + 稀疏 −0.001） | **不受影响**。那测的是"加容量"，本实验测的是"分配隔离" |
| 84M ID embedding 是死重（E1 PASS） | **被使用**：正因如此才能用 0.58M 模型跑 58 run |
| pooled 端点上 MoE 无稳定优势 | **维持**。本实验预期 pooled 端点仍无显著变化（§4.3） |

**本实验测的是一个此前从未被测过的机制**：不是容量，是**跨场景干扰的隔离**；不是 pooled，是 **macro**。

## 二、设计：容量恒定，只变"隔离"与"梯度均衡"

### 2.1 关键性质：参数量守恒

`model.CrossExpertLayer` 把 `Linear(dim,dim)` 拆成 **K 个 `Linear(dim, dim/K)`** 后 concat，
所以总参数**精确守恒**：

```
moe 参数 − dense 参数 = 3 层 × 15 场景 × K = 45K
K=5 → 225 参数（占 584,255 的 0.04%）
```

实测：dense `584,255` vs moe(K=5) `584,480`，差 **225**。且 router 权重零初始化 → softmax uniform
→ `×K` 后 **gate ≡ 1.0**（实测 `gate_mean_init=1.0`），此时 concat 的 K 个专家在代数上**等价于
一个 `Linear(dim,dim)`**。

**因此任何收益都不可能来自容量**——这直接沿用并尊重了 dense-widened 的结论。K 扫描是**纯隔离粒度**
扫描（K 变化不改变参数量）。

### 2.2 2×2 主设计

| 维度 | 取值 | 被测机制 |
|---|---|---|
| `arch` | `dense` / `moe`(K=5, scenario routing) | **参数隔离** |
| `loss` | `pooled` / `balanced` | **梯度均衡** |

- `pooled` = full-batch BCE（历史口径，已验证等价 sample-weighted）；
- `balanced` = 对 batch 中**出现的每个场景**各算其自身 BCE 均值，再等权平均
  （向量化 `scatter_add_` 实现，**零 host sync**，沿用 11× 吞吐优化的纪律）。

为何两者都要测：**光有 MoE 而 loss 仍被 65% 的 s1 主导，梯度依然压制小场景**；反之光有 balanced loss
而参数共享，容量竞争依然存在。2×2 才能把两个机制分开归因。

### 2.3 模型选择必须对齐主终点

**best epoch 由 macro *valid* AUC 的精确 argmax 选出**（不是 pooled valid，不用 0.001 死区）。
若用 pooled valid 选点，就会重新引入 §1 的口径错配——这是本实验最容易犯的自伤错误，故显式冻结。

### 2.4 主终点与场景集合（启动前冻结）

- **主终点** = `MACRO_SCENARIOS = (0,1,2,3,4,5,6,8)` 上的 test AUC 等权平均。
- 该集合**不是事后挑选**：s9/s10/s13 在 test 全为正类、s11 全为负类（AUC 无定义），s14 test 零样本，
  s7 仅 423 条 test（方差过大不宜进主终点）。剩下的恰好等于代码里既有的
  `GradientTracker.TARGET_SCENARIOS`。
- s7 / s12 为**辅助报告**（`AUX_SCENARIOS`），**永不进入判定**。

## 三、矩阵（58 run，任务表即预注册，启动前冻结）

`scripts/run_macro_auc_matrix.py` 的 `build_tasks()` 就是本表；**启动后不得增删配置**。

| Stage | 内容 | run 数 | 目的 |
|---|---|---|---|
| **S1（主）** | 2 arch × 2 loss × 4 seed | **16** | 主判定 + 两机制分解 |
| **S2（哨兵）** | moe + `--freeze-router` × 2 seed | 2 | 函数保持：gate≡1 时须与 dense 一致 |
| **S3** | K ∈ {2,3,6,10,11} × balanced × 4 seed | 20 | 隔离粒度扫描（容量恒定） |
| **S4** | lr ∈ {2e-4, 3e-3} × 2 arch × 4 seed | 16 | lr 稳健性（1e-3 由 S1 覆盖） |
| **S5** | 84M 全 embedding × 2 arch × 2 seed | 4 | 结论是否依赖轻量模型 |

- seeds = **42, 123, 456, 789**（4 seed，强于此前的 2–3 seed）。
- **配对保证**：`SEED_DEVICE = {42:cuda:0, 456:cuda:0, 123:cuda:1, 789:cuda:1}` —— 同一 seed 的
  **全部配置固定同卡**（AGENTS.md 规则），不同 seed 跨卡并行。
- 口径：`lr=1e-3`、`batch=10000`、`max_epochs=80`、`patience=12`（基于 macro valid）、
  轻量模型（iddrop，E1 PASS 授权）、GpuBatches。
- K 必须整除 dim=330（330 = 2·3·5·11），故 K ∈ {2,3,5,6,10,11}；**K=4 不可用**（会与
  `dim % K == 0` 断言冲突，脚本会显式报错而非静默取整）。
- 实测 10.2s/epoch → 单 run ≈ 8–15 min，58 run 双卡各 29 → **预计 7–9h**，预算上限 11h。

## 四、判定规则（启动前冻结，硬编码于 `scripts/summarize_macro_auc.py`）

### 4.1 主终点

```
Δ_moe(seed) = macro_test(moe, balanced, K=5) − macro_test(dense, balanced)
```
同 seed 配对（同卡由构造保证）。

### 4.2 噪声地板必须实测，不能沿用 0.001

pooled AUC 的 0.001 地板**不适用于 macro**：macro 是 8 个场景的等权平均，含小样本场景，
run 间波动更大。故：

```
floor = 2 × SD( dense+balanced 臂的 macro AUC 跨 4 seed )
```

这是**用同一批 run 的内部对照估计**的，且是 dense 臂自身的波动，**无法在看到 MoE 结果后调整**。

### 4.3 判定表

| 判定 | 条件 | 后续 |
|---|---|---|
| **PASS** | 4/4 seed Δ_moe > 0 **且** mean(Δ_moe) > floor | 首个 work case 成立：MoE 改善场景内泛化。解锁 K/粒度与真实稀疏化的后续设计 |
| **FAIL** | 4/4 seed Δ_moe < 0 | 连 macro 端点也无收益 → MoE 在本任务上全面关闭 |
| **INCONCLUSIVE** | 跨 seed 变号，或效应落在 floor 内 | 不解释部分结果；只允许按原口径扩 seed，不得改端点/阈值 |
| **BLOCKED** | S1 缺 run，或 **S2 函数保持哨兵失败**（\|Δ\| > 0.010） | 不得解读任何数字 |

### 4.4 禁止项（预注册）

- 不得事后更换 `MACRO_SCENARIOS`（例如把 s7/s12 加进来凑正结果，或把不利场景踢出去）；
- 不得改用 pooled valid 选 best epoch；
- 不得用跨 seed 均值掩盖变号；
- 不得把 macro 收益与历史 pooled 数字放同一张表比较（两个端点不可混用）；
- **若 macro 涨而 pooled 跌，必须如实报告为 trade-off**，不得隐藏；
- 不得因 S3/S4/S5 中某个配置好看就改写 S1 的主判定地位；
- S3/S4/S5 仅在 S1 判定为 PASS 时具有解释力（否则是在无效应上做子群挖掘）。

## 五、预期与可反驳性

- **预期方向**：Δ_moe > 0，且收益主要来自 s5/s8/s3/s6 这些小场景（此前被 s1 压制的）。
- **同一批 run 会同时报告 pooled 端点的 Δ**。若 `|Δ_macro| >> |Δ_pooled|`，即**定量证明
  §1 的诊断**（旧端点测不到该机制）。这一列本身就是本实验最重要的方法论产出。
- **可反驳**：若 4/4 seed Δ_moe < 0，则 MoE 在本任务上连场景内泛化都救不了，
  应彻底关闭 MoE 方向——本实验设计允许这个结论干净地出现。

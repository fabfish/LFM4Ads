## 一、审计结论：主体成立，一条推断必须修订

### 1.1 站得住的部分（确认，不改判）

逐条复核 `HANDOFF.md` §1 与 `ANALYSIS.md` §2.6 的证据链，**以下全部成立**：

| # | claim | 证据 | 复核结果 |
|---|---|---|---|
| 1 | cross 层容量不是 AUC 瓶颈 | dense-widened 4×（加宽+非线性、零路由零稀疏）Δ_capacity={+0.0005,−0.0003,+0.0001,−0.0005}，跨 seed/lr 变号、\|Δ\|≤0.0007 | **成立**。变量干净（同 seed 同卡、freeze sparse、参数量精确 4.00×），结论未越证据 |
| 2 | capacity-MoE 收益 = 容量收益(≈0) + 稀疏代价(≈−0.001) | `top_k=K` 4 run 变号 / `top_k=2` 4/4 同号为负 | **成立**。分解逻辑正确，稀疏代价是唯一 MoE 独有项 |
| 3 | 三处修复（embedding 解冻共因 / lb 8× / host-bound） | Δ_necessity −0.0019→−0.0003、lb 0.0807→0.0081、GpuBatches 等价性 \|ΔAUC\|=0 | **成立**，且修复方向正确 |
| 4 | router 特化机制成立但≠收益 | 熵 1.386→0.74、12/12 dispatch 哨兵 PASS | **成立**，机制/收益已正确分离 |
| 5 | 核心教训"加容量前先证伪容量缺口" | 由 #1 直接得出 | **成立**，且本轮立即用它挡掉了一个错误实验（见 §1.2） |

**capacity-MoE 关闭的判定不受本次修订影响**：它由 #1+#2 独立支撑，与 embedding 侧的解释无关。

### 1.2 必须修订的一条：「瓶颈在 embedding」是过度推断

三处文档（`HANDOFF.md` §0/§1.A3、`ANALYSIS.md` §2.6/§4.3、`NEXT.md` §3.2）都写着同一句推断：

> 瓶颈在 **embedding 表（97.9% 参数）**，不在 cross 层（0.46%）。

**这一步是无依据的跳跃**，理由有二：

1. **"参数最多"≠"瓶颈"**。这正是 cross 层 MoE 犯过的错的镜像版本——上游刚刚用 dense-widened
   证明"给某处 4× 容量换不到收益"，却随即用"参数占比"这个同类指标去推断新的瓶颈位置。
2. **原文引用的证据方向被读反了**。`ANALYSIS.md` §4.3 用"冻结 embedding 后两臂绝对 AUC 反而更高
   （0.7816 vs 0.7811）"来支持"瓶颈在 embedding"。但"冻结后更好"恰恰说明这些参数是
   **过拟合负担（burden）**，不是**受限的瓶颈（bottleneck）**。同一事实不能同时支持两个相反的读法。

本次用**两个零训练成本的诊断**把这条推断彻底证伪（§2、§3）。修订后的正确表述见 §4。

### 1.3 顺带修掉的文档不一致

- `DRIVERS.md` §4 末尾引用 `NEXT.md` **§7.2**，但 `NEXT.md` 只有 §1–§3，正确锚点是 **§3.2**。
- `NEXT.md` §3.2 与 `HANDOFF.md` §4 把"embedding-widened 加宽对照"列为下一步第一实验；
  经 §3 证据，该实验**已无需执行**（前提被证伪），改为 §5 的 E1。

## 二、E0（零成本证据）：84M 参数长什么样

脚本 `scripts/diagnose_embedding_capacity.py`，产物 `cache/embedding_capacity/diagnosis.json`（不可覆盖）。

**样本计数（冻结为后续哨兵基线）**：train `9,281,007` / valid `1,230,368` / test `1,201,670`，合计 `11,713,045`。

### 2.1 参数集中度：99.96% 在三个超高基数 ID 字段

| 组 | 参数 | 占 embedding |
|---|---|---|
| `video_id` + `author_id` + `music_id` | **83,984,250** | **99.9606%** |
| 其余全部 33 个字段合计 | **33,140** | 0.0394% |
| 合计 | 84,017,390 | 100% |

即所谓"97.9% 的参数"实际上就是三张 ID 表；其余 33 个字段的 embedding 加起来只有 3.3 万参数。

### 2.2 监督极度稀薄 + test 期大规模 OOV

| 字段 | vocab | train 中出现 | 平均曝光/id | 曝光≤2 次的 id 占比 | **test 样本 OOV 率** |
|---|---|---|---|---|---|
| `video_id` | 4,369,953 | 3,560,309 | **2.6** | **79.83%** | **74.19%** |
| `music_id` | 2,621,019 | 2,165,468 | 4.3 | 74.27% | 47.58% |
| `author_id` | 1,407,453 | 1,200,151 | 7.7 | 63.64% | 17.10% |
| `upload_dt` | 236 | 230 | 40,352 | 2.17% | 62.07%（时间漂移） |
| `tag` | 1,189 | 1,145 | 8,106 | 34.41% | 0.00% |
| `user_id` | 1,000 | 998 | 9,300 | 0.00% | 0.07% |

- **17.53%（14,725,500）的 embedding 参数从未收到任何梯度**（对应 train 中未出现的行，永久停留在随机初始化）。
- test 中 **74.19% 的样本，其 `video_id` 行在训练期从未被更新过**——这些样本的 video_id 通道读到的是随机数。

**推论**：`video_id` 这类字段的问题不是"每行 10 维不够宽"，而是"每行平均只有 2.6 个样本可学，
且线上 3/4 的流量根本没有对应的行"。在这种结构下加宽（10→20 维）只会把随机数从 10 维变成 20 维。

## 三、E0b（零成本证据·决定性）：84M 参数对预测的实际贡献 ≈ 0

脚本 `scripts/diagnose_field_ablation.py`，产物 `cache/embedding_capacity/field_ablation.json`（不可覆盖）。

方法：加载既有冻结 dense ckpt（`cache/dcnv2_vanilla.pt`，即 Arm A，test AUC `0.777490`），
**推理期**逐字段把该字段 embedding 表置零（该通道输出恒为 0 向量，维度不变），测 pooled test AUC 变化。

### 3.1 主结果：把 83,984,250 个参数全部清零，AUC 只掉 0.000193

| 消融对象 | 参数 | test AUC | Δ |
|---|---|---|---|
| — （基线） | — | 0.777490 | — |
| **`video_id`+`author_id`+`music_id` 同时清零** | **83,984,250** | 0.777297 | **−0.000193** |
| `video_id` 单独 | 43,699,530 | 0.777472 | −0.000018 |
| `music_id` 单独 | 26,210,190 | 0.777525 | **+0.000035** |
| `author_id` 单独 | 14,074,530 | 0.777353 | −0.000138 |

**−0.000193 远低于噪声地板 0.001**，且比本仓库任何一次"无效应"判定的 |Δ| 都小。

### 3.2 对照：全部预测能力来自 ~3 万参数的低基数字段

| 字段 | vocab | 参数 | Δ_AUC |
|---|---|---|---|
| `tag` | 1,189 | 11,890 | **−0.006555** |
| `upload_type` | 32 | **320** | **−0.005251** |
| `user_id` | 1,000 | 10,000 | −0.004879 |
| `onehot_feat1` | 7 | **70** | −0.002973 |
| `onehot_feat3` | 394 | 3,940 | −0.002356 |
| `onehot_feat8` | 283 | 2,830 | −0.002184 |
| `onehot_feat7` | 37 | 370 | −0.001842 |
| `follow_user_num_range` | 8 | 80 | −0.001648 |

- top-8 依赖字段合计 **29,500 参数 = embedding 的 0.035%**，每一个的单字段 Δ 都比 84M 三大 ID
  **合计**的 Δ 大 8–34 倍。
- `upload_type`（**320 参数**）的贡献是 `video_id`（**43.7M 参数**）的 **292 倍**。
- 有 4 个字段消融后 AUC 反而**上升**（`onehot_feat15/16/17`、`visible_status`、`music_id`、`video_type`），
  量级 +0.00004~+0.00012，属噪声，但方向一致地说明这些通道无正贡献。

### 3.3 结论边界（启动前登记，事后不得放宽或收紧）

- E0b 测的是**已训练模型的依赖度（dependence）**，不是**重训练下的必要性（necessity）**——
  模型没有机会重新分配容量，因此本方法**系统性高估**字段重要性。
- 由此可安全推出的**只有一个方向**：Δ≈0 的字段**不可能**是容量瓶颈（高估都测不出贡献）。
  反之，Δ 大的字段只是"候选"，不能直接称必要。
- 因此 E0b 足以**关闭 embedding 加宽路线**，但"84M 可直接删除"这一工程 claim 必须由 §5 的 E1
  在**重训练**口径下确认，方可写进结论。
- 子群 AUC（video_id seen `0.776274` / OOV `0.777041`）**不做跨子群比较**（基率与难度不同），
  只登记为 provenance。

## 四、修订后的 claim 表（替换上游三处表述）

| # | 上游 claim | 本轮证据 | 修订后判定 |
|---|---|---|---|
| 1 | 「瓶颈在 embedding 表（97.9% 参数）」 | 三大 ID 表全部清零 Δ=−0.000193（噪声内）；17.53% 参数从未有梯度；test 74% video_id OOV | **证伪 → 改判**：84M ID embedding 是**死重 + 过拟合负担**，不是瓶颈 |
| 2 | 「下一步做 embedding-widened 加宽对照」 | 现有容量已被证明**未被用上**，加宽的前提不存在 | **撤销该实验**（零成本挡掉一次 GPU 长跑） |
| 3 | 「冻结 embedding 后 AUC 更高 ⇒ 瓶颈在 embedding」 | 同一事实的正确读法是"这些参数是负担" | **方向修正**：burden ≠ bottleneck |
| 4 | 「模型侧全部证伪则问题在数据/任务」 | 有效输入信息集中在 ~3 万参数的 33 个低基数字段；长尾 ID 通道几乎不携带可泛化信号 | **细化**：不是笼统的"数据不行"，而是**特征信息侧**——长尾 ID 的可泛化表示缺失 |
| 5 | cross 层容量非瓶颈 / capacity-MoE 关闭 | 见 §1.1 | **维持**，不受本修订影响 |

**新的统一图景（一句话）**：这个任务上，**cross 层不缺容量、embedding 表容量根本没被用上**——
AUC 0.78 的天花板来自**可用输入信息量**，而 84M 参数的长尾 ID 通道在当前建模方式下没有把信息交出来。

## 五、E1 预注册：ID embedding 死重的重训练确认（启动前冻结）

### 5.1 主张与用途

- **claim**：三大 ID 字段（83,984,250 参数 = 总参数 97.9%）在**从零重训练**口径下对 test AUC
  无可测贡献。
- **为何必须做**：E0b 是推理期消融，模型未重新分配容量；只有重训练才能把
  "死重" 从**依赖度**升级为**必要性**结论。这是唯一能把 §3 写进 `ANALYSIS.md` 高置信区的实验。
- **附加价值（阶段性产出）**：若成立，则后续所有实验的模型从 85.8M 参数降到 ~1.8M，
  训练/显存成本骤降，可负担 3 seed 甚至更多；同时得到一个可直接汇报的工程结论
  （参数 −97.9%、AUC 不变）。

### 5.2 三臂设计（除被测项外完全一致）

| 臂 | 名称 | 说明 | 输入信息 | 架构 |
|---|---|---|---|---|
| **A** | `full` | 36 字段全 embedding，从零训练 | 全部 | dim=360 |
| **B1** | `idzero` | 三大 ID 表**置零且冻结**（`requires_grad=False`，通道恒 0 向量） | 去掉 ID | **dim=360，与 A 完全同构** |
| **B2** | `iddrop` | 三大 ID 字段真正移除 | 去掉 ID | dim=330（量化工程收益） |

- **B1 是主对照**：架构、维度、层参数量与 A 逐一相同，唯一差异是三个通道被钉在 0
  → 干净隔离"ID embedding 的贡献"。
- **B2 是工程对照**：报告参数量、wall-clock、显存的实际收益。因 dim 变化会连带缩小 cross 层，
  而"cross 层容量无效应"已由 dense-widened 独立证实，故不构成混淆因子；但 B2 **不作为主判定**。

### 5.3 口径（冻结）

```
from scratch（不加载任何 ckpt）
GpuBatches GPU 常驻数据 + full-batch BCE（无 per-scenario 拆分，三臂一致）
optimizer=AdamW, lr=1e-3, betas=(0.9,0.999), batch_size=10000, max_epochs=15
best_state = 精确 argmax(valid AUC)（不使用 0.001 死区）
seeds = {42, 123}，同一 seed 的三臂在同一进程内顺序执行 → 同卡天然保证
  （s42→cuda:0，s123→cuda:1），每臂开始前重置 torch.manual_seed(seed)
主指标 = best-valid-state 的 pooled test AUC；辅助 = peak valid AUC、wall/epoch、参数量
```

- `lr=1e-3` 沿用**从零预训练的历史口径**（`train.py:train()` 的 AdamW 默认值，即 `dcnv2_vanilla.pt`
  test AUC 0.7775 的口径），使 A 臂可与历史基线对照。`lr=2e-4` 是"继续训练"场景的最优值，
  不适用于 from-scratch，仅在 E1 出现 INCONCLUSIVE 时作为 robustness 复核（不改判定规则）。
- 已知 `lr=1e-3` 下 84M embedding 会过拟合（上游根因 1）。这**不影响公平性**：三臂同等施加，
  且主指标取 best-valid-state，峰值前的过拟合不进入判定。
- 这里**不能**使用 `--freeze sparse`——embedding 正是被测对象，必须三臂同等**可训练**。

### 5.4 启动前哨兵（全部 PASS 才允许跑正式矩阵）

| # | 哨兵 | 判据 |
|---|---|---|
| S1 | 样本计数守恒 | train/valid/test = 9,281,007 / 1,230,368 / 1,201,670（与 E0 冻结值一致） |
| S2 | B1 置零语义 | 训练前后三表 weight `abs().max()==0`，且 `requires_grad==False` |
| S3 | B1 通道恒零 | 一个 batch 的 embed 输出在三 ID 对应的 30 维切片上 `abs().max()==0` |
| S4 | 可训练参数差 | `A − B1 == 83,984,250`（精确） |
| S5 | 配对一致性 | 同 seed 的 A/B1/B2 同卡、同 lr、同 batch、同 epochs、同数据顺序种子 |
| S6 | 非被测项不变 | A 与 B1 的 cross/DNN/head 参数量完全相同 |

### 5.5 判定规则（冻结，事后不得更换阈值）

噪声地板沿用既有口径 **0.001**（依据：dense-widened 与 reinit 矩阵中同配置跨 seed/lr 的
|Δ| ≤ 0.0007 全部判为无效应）。主指标 Δ_id = **B1 − A**（同 seed 配对差）。

| 判定 | 条件 | 后续动作 |
|---|---|---|
| **PASS（死重成立）** | 2/2 seed \|Δ_id\| < 0.001 | ID embedding 无净贡献 → embedding 容量路线**正式关闭**；后续实验默认切到 B1/B2 轻量模型；方向转 §6 |
| **FAIL（ID 有贡献）** | 2/2 seed Δ_id ≤ −0.001（同号） | 长尾 ID 确实携带信号 → "如何更好地表示长尾 ID"成为**有证据支持**的方向（此时且仅此时可议条件化容量） |
| **INCONCLUSIVE** | 跨 seed 变号，或落在 (−0.001, 0) 与 0.001 边界不一致 | 不解释部分结果；只允许扩 seed 456 一次，不改口径 |
| **BLOCKED** | 任一哨兵 FAIL / run 缺失 / 崩溃 | 不得解读任何数字 |

**禁止项**（预注册）：不换阈值凑正结果；不按臂重采样；不用单 seed 下结论；不用 valid AUC 替代
test 主终点；不因 B2 结果好而改 B1 的主判定地位；不把 wall-clock/参数量收益写成 AUC 收益。

### 5.6 成本

| 项 | 估算 |
|---|---|
| 单臂（15 epoch，GpuBatches） | ≈ 2–5 min |
| 单 run = 三臂顺序（同 seed 同卡） | ≈ 8–15 min |
| 矩阵 2 seed（双卡并行 2 run） | **≈ 15 min** |
| GPU | s42→cuda:0，s123→cuda:1 |

## 六、E1 之后的分支（条件解锁，不预先执行）

### 6.1 若 E1 = PASS（预期路径）

问题正式从"容量"转到"**信息与泛化**"。按性价比排序，均需各自预注册：

1. **E2 长尾 ID 的可泛化表示**：ID 本身不可泛化（test 74% OOV），但其**属性**可以。
   把 `video_id`/`author_id`/`music_id` 替换为频次分桶 + 统计特征（历史 CTR 的时序安全编码、
   作者侧聚合、tag/upload_type 交叉），对照 B1。判据：是否越过 0.001 地板。
   这是 E0b 直接指出的方向（`tag`/`upload_type` 这类 300–12,000 参数的字段贡献最大）。
2. **E3 特征交互侧表达**：在轻量 B1 模型上加 FM/attention 式高阶交叉，参数量匹配对照。
   此时模型只有 ~1.8M 参数，可负担 3 seed × 多配置。
3. **E4 天花板定位**：用 33 个低基数字段能达到的 AUC 上界（如 GBDT/更强 head 对照），
   判断 0.78 是"模型不足"还是"信息不足"。

### 6.2 若 E1 = FAIL

说明 ID 通道在重训练下确有贡献，则：先做 **ID 侧容量-性能斜率扫描**（embed_dim ∈ {2,5,10}
下探，成本低于加宽），确认曲线是否已饱和；只有在斜率显著非零时，才允许讨论 ID 侧的
条件化容量（此时 MoE 类结构才第一次有前提）。

### 6.3 仍然关闭的路线（不变）

capacity-MoE（cross 层）、Stage B same-FLOPs、TCMR 静态路由、共享残差持续学习、下游留出域迁移。
